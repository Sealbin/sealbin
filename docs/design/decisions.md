# Design decisions

The decisions behind the issues in this repository, recorded when they were
written (2026-10-02). Issues cite them as D1, D2, …. A decision changes by
pull request to this file, with the issues that depend on it updated in the
same change.

The "verified facts" sections describe the Cratefield harness at
`Cratefield/harness` origin/main a3ff67f and the Owlpost backend as of the
same day; check the code before relying on a line number.

## Product decisions (apply consistently)
D1 Repo sealbin/sealbin, Apache-2.0, Rust workspace:
  crates/sealbin-format (pure, no I/O, native+wasm32: link, envelope, chunked AEAD, KDFs, tokens, bundle)
  crates/sealbin-core (pure server domain: seal state machine, plans as data, ids, limits)
  crates/sealbin-server (harness modules: seals, agents, accounts, billing, audit, device wiring) — module crate(s) inside one crate with feature-free modules `seals`, `agents`, `accounts`, `billing`, `audit`, `teams`
  crates/sealbin-worker (cdylib venture: Harness composition, `SealObject` Durable Object class, wrangler.toml, migrations/, static assets for /s/ and /activate)
  crates/sealb (CLI binary; includes `sealb mcp` stdio MCP server via the `rmcp` crate)
  crates/sealbin-wasm (wasm-bindgen wrapper over sealbin-format for the browser page and `@sealbin/crypto`)
  npm/ (packages: `sealb` wrapper, `@sealbin/mcp` wrapper that execs `sealb mcp`, `@sealbin/cli-{darwin-arm64,darwin-x64,linux-x64-gnu,linux-arm64-gnu,linux-x64-musl,win32-x64}`, `@sealbin/crypto` wasm)
  skill/ (SKILL.md and references), web/ (open + activate pages, vanilla JS like the site), spec/ (handoff format), docs/ (design, threat model, runbooks), deploy/ (self-host)
  Issue 01 creates every crate as a compiling stub so later issues never edit the workspace member list.
D2 Harness deps: cratefield-* from crates.io on the 0.6 line; when a needed harness change is unreleased, pin ALL cratefield-* to one git rev (never mix; two copies of core error). Not factory0-*.
D3 Hosts: hosted API https://api.sealb.in; links https://sealb.in/s/<id>#key=<k>. Worker routes `sealb.in/s/*`, `sealb.in/activate*` and `sealb.in/.well-known/sealbin` to the sealbin Worker; the rest of sealb.in stays on Pages. Clients resolve the API from the link host with `GET https://<host>/.well-known/sealbin` -> {"api": "...", "formats": [1], "limits": {...}} (cached). Self-host and custom domains: one host serves links, pages and API.
D4 Link: `https://<host>/s/<id>#key=<base64url-nopad 32 bytes = 43 chars>`. id = 12 chars base62 from CSPRNG (~71 bits). (Site examples show 8-char ids; cosmetic.) Recipient-locked v2 links carry no key.
D5 Crypto v1 (all WebCrypto-implementable): K_link 32 random bytes. Optional password: P = PBKDF2-HMAC-SHA256(NFC UTF-8 password, salt16 from header, iterations from header, default 600,000, 32 bytes). IKM = K_link || P (or K_link alone). HKDF-SHA256(IKM, salt = header.nonce16): info "sealbin/v1/payload" -> K_payload (AES-256-GCM key); info "sealbin/v1/read" -> read_token (32 bytes). Payload = STREAM: 64 KiB plaintext chunks, AES-256-GCM, 12-byte nonce = 11-byte big-endian chunk counter || last-chunk flag byte (0x00/0x01); AAD = SHA-256(header bytes). Envelope = magic "SEALBIN" + version byte 0x01 + fixed binary header (flags incl. password bit, kdf iterations u32, salt16, nonce16, chunk size u32) + chunks. Plaintext = u32 BE inner-meta length + inner meta JSON {kind: "file"|"bundle"|"text", name?, content_type?, size?, created_at} + content. bundle = POSIX tar (pax). Everything except the fixed header is encrypted (server never sees names).
D6 Read token: sealer sends read_verifier = SHA-256(read_token) at creation. Opening requires presenting read_token, so nobody without the key (and password) can burn a seal: unfurl bots, log readers of the path, guessed ids. Wrong token -> 403 `seal/wrong-key`, does not burn, per-seal failure backoff (never destroys the seal; open decision whether to cap).
D7 Server-visible metadata: id, ciphertext size, created_at, expires_at, burn flag, read state, password flag (visible in header bytes anyway), sealing API key/agent and account. The site FAQ omits the password flag -> launch checklist item to make site, FAQ JSON-LD and llms.txt agree.
D8 Lifecycle: states sealed -> opening -> gone (burn) ; sealed -> gone (ttl/revoke). Default = burn after first read, expires unopened after 24 h (or --ttl, up to plan max). `--ttl` alone = readable many times until expiry; `--ttl X --burn` = whichever first. First successful open atomically moves sealed->opening and returns a reopen_token (32 random bytes, hash stored). "Same agent" = holder of that reopen_token. Within 60 s of the first open, `reopen` with the token streams the ciphertext again; `ack` deletes at once; the 60 s alarm deletes otherwise. Every other open after the first gets 410 `seal/gone`. The CLI writes the reopen token to ~/.local/state/sealb/pending/<id> (0600) before reading the body, so a crashed process can resume.
D9 Storage: one Durable Object per seal (`SealObject`, name = seal id) is the authority on state; ciphertext <= 1 MiB inline in DO storage, larger in R2 at `seals/<id>` via multipart (parts <= 50 MiB, Workers request-size limit). D1 holds a metadata index only (account, agent, size, created, expires, state) for limits, audit and listing. No R2 versioning, no backups of ciphertext; R2 lifecycle rule deletes `seals/` objects older than max TTL + 1 day as a backstop; D1 Time Travel holds metadata only (documented).
D10 API (v1, problem+json errors via harness Problem): module `seals`: POST /v1/seals (small, binary body `application/vnd.sealbin.v1`, headers Sealbin-Read-Verifier, Sealbin-TTL, Sealbin-Burn), POST /v1/seals/uploads, PUT /v1/seals/uploads/{uid}/parts/{n}, POST /v1/seals/uploads/{uid}/complete, GET /v1/seals/{id} (metadata, never burns, no auth), POST /v1/seals/{id}/open {read_token} -> ciphertext + Sealbin-Reopen-Token header, POST /v1/seals/{id}/reopen, POST /v1/seals/{id}/ack, DELETE /v1/seals/{id} (sealer). `/.well-known/sealbin` from the seals module. Modules `agents` (/v1/agents: list/create/rename/revoke keys, scopes), `accounts` (/v1/accounts/me, usage), `device` (C04 module at /v1/device), `billing` (/v1/billing/checkout, /portal, /stripe-webhook), `audit` (/v1/audit), `teams` (/v1/teams, M1 Team). Opening needs no API key; when one is sent the open is attributed in the audit log.
D11 Accounts & sign-in: hosted accounts sign in via the Factory Zero auth service (auth.factory0.ventures, sealbin registered as a client), tokens verified with cratefield-auth-client (Auth port). CLI and MCP get an API key through device authorization (Cratefield/harness issue 05 module) approved at https://sealb.in/activate. Self-host: no FZ auth; ADMIN_TOKEN-gated approval and `sealb admin` commands.
D12 API keys: harness ApiKeys namespace `sb` -> `sb_live_<id>_<secret>` / `sb_test_...`. Site placeholder `sk_live_…` must change (launch checklist). An "agent" = one named API key; plan agent limit counts active keys. `sealb init` creates one key per machine (name = hostname) shared by the agents it wires; `--key-per-agent` makes one per agent. (Open decision.)
D13 Plans (as data in sealbin-core, labelled planned on the site): Free 3 agents, 1,000 seals/month during launch (250 after), 5 MB, TTL <= 24 h; Pro $19/mo 10 agents, unlimited seals (fair use rate limits), 100 MB, TTL <= 30 d, per-agent key scopes, audit log; Team $49/mo 50 agents, custom domain, policies & roles, 1-year audit, region; Self-host unlimited. Seals counted per account per UTC calendar month on successful creation; opens never counted. Size limit applies to ciphertext.
D14 Email: harness Mailer + adapter-owlpost (Cratefield/harness issue 09), from no-reply@send.sealb.in. Sealbin sends: plan/limit notices, billing notices, (M2) receipts. Sign-in mail is the auth service's.
D15 CLI in Rust; npm distribution esbuild-style (optionalDependencies per platform); also GitHub release binaries and `cargo install sealb`. Node >= 18 only to run npx. Config: XDG config dir `sealb/config.toml`; key in OS keychain when available, else 0600 file; env SEALB_API_KEY, SEALB_SERVER.
D16 Open output: `sealb open <link>` with kind=file writes bytes to stdout when stdout is not a TTY, else to ./<name>; `--to <dir>` writes/extracts there; MCP `open` requires `to`. Extraction refuses absolute paths, `..`, symlinks, hardlinks, devices; never sets exec bits; caps file count and total size. Skill layout memory/handoff-<id>/ with INDEX.md first and `.sealbin-untrusted` marker.
D17 Agents to wire (verify current docs; record verified paths + doc URL + date in docs/agents.md): Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot (VS Code), Windsurf, Hermes Agent, GitHub Actions. Site paths (to verify): Codex ~/.codex/config.toml [mcp_servers.sealbin]; .cursor/mcp.json; ~/.gemini/settings.json; .vscode/mcp.json (servers, type stdio); ~/.codeium/windsurf/mcp_config.json; ~/.hermes/config.yaml mcp_servers; Claude Code `claude mcp add sealbin -- npx -y @sealbin/mcp`.
D18 No server-side scanning (E2E). Local scanners M2.
D19 The "Built with" list (`sealb about`, web/open.html) is generated at build time from a vendored copy of Sealbin's Factory Zero registry entry (`crates/sealb/data/stack.json`, FZ-016); there is no runtime fetch, the registry is authoritative and changes first, a network-gated test fails when the copy drifts, and nothing planned may ever be shown as live.
